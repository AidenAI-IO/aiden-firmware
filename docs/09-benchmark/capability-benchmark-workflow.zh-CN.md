# 从一个任务讲清 Benchmark：怎样知道 Aiden 变好了

这是一份可以直接用于团队分享的讲解稿。建议用 20 分钟，围绕同一个任务，从用户遇到的问题讲到一次优化的验收。每一步只在需要时引入新的指标。

听众最后应能做到三件事：判断一次评测是否说明问题、从失败中选择一项修改、说明需要什么证据才能接受修改。

字段定义留在[指标参考文档](./metrics-and-optimization.zh-CN.md)，分享时不需要逐项讲。下面的数字均为教学示例，不是当前 Aiden 的实测成绩；历史失败会单独标明，当前尚未完成这个案例的真实前后优化实验。

## 开场：先讲一个用户会遇到的问题（1 分钟）

可以这样开场：

> 用户之前让 Aiden 记住“我喜欢深色模式”。今天他改主意了，说“以后请用浅色模式”。Aiden 回答“已经更新好了”。我们能因此认为这项能力已经做好了吗？
>
> 我们今天就用这一件小事，讲清楚怎样知道 Agent 做对了，以及修改之后是不是真的更好了。

屏幕上只放这三句话：

```text
之前：记住我喜欢 dark mode。
现在：我改主意了，以后请用 light mode。
Aiden：已经更新好了。
```

此时先不展示 Langfuse，也不解释 pass@k。听众需要先理解为什么“看起来完成”还不足以证明“真的完成”。

**接到下一步：**“既然一句确认不够，我们先约定什么结果才算做对。”

## 第一步：把“做对了”说清楚（2 分钟）

对于这个任务，产品上的成功应该是：新偏好已经保存；之后的新对话会使用浅色模式；旧偏好不会继续作为有效的冲突信息影响回答。

可以这样讲：

> Benchmark 的第一件事是出一道有标准答案的题。我们先把起点固定为“已保存深色偏好”，再提出修改要求，最后检查记忆和后续回答。这样，大家讨论的就是同一件事。

画出这条最短链路：

```text
已确认保存旧偏好 → 用户要求修改 → 检查新记忆 → 新对话验证新偏好
```

仓库已经有 `memory_v1/update_changed_preference`：它检查更新过程中是否召回旧偏好、保存新偏好并确认更新。**现有题目主要检查更新交互，还不能单独证明持久化状态和新对话召回正确。** 后两项需要补充证据；如果加入题目，两个版本都必须使用同一份新定义。

一项任务定义清楚后，再扩展到一组代表性任务，例如保存事实、修改偏好、遗忘记忆。手机操控则可以另选打开联系人、调整播放速度等真实需求，形成 MobileBench。20–50 个固定任务可以作为初始核心集的目标，先保证任务可重复、结果可验证。

**这一页让听众记住：先约定用户结果，再讨论评分。**

**接到下一步：**“有了固定的题，我们就可以问：Aiden 到底能做对多少？”

## 第二步：先看做对了多少（3 分钟）

先用白话讲成功率，再给字段名。

> 假设有 10 道固定任务，每题跑一次，6 道成功。我们能直接说成功率是 60% 吗？先看另外 4 道发生了什么。

展示这张教学结果表：

| 结果 | 数量 | 是否能判断 Agent 能力 |
| --- | --- | --- |
| 已执行、结果正确 | 6 | 可以，计成功 |
| 已执行、结果不正确 | 2 | 可以，计失败 |
| Agent 未就绪，无法正常执行 | 1 | 不可以，需排查运行环境 |
| 评估所需证据缺失，无法判定 | 1 | 不可以，需补齐评估证据 |

于是这轮应报告：**计划 10 道，10 道都有记录，8 道有效；成功 6/8，即 75%；另有 2 道无法有效评估。** 有效覆盖率为 80%。不能只展示 75%，也不能把两道无效题当成已经通过。

到这里才介绍第一个能力指标：`capability.pass_at_1`，表示任务实际第一次尝试的成功比例，分母是第一次尝试有效的任务。

如果有人问“怎么区分做错和没测出来”，只解释三个字段：

| 字段 | 在这个问题中的作用 |
| --- | --- |
| `status` | 这次尝试最后被记录成成功、失败、超时、评估错误还是跳过 |
| `agent_eligible` | 是否进入能力统计的分母 |
| `failure_class` | 出问题时先沿哪一大类排查，尚不是具体根因 |

`status=skipped` 与 `failure_class=skipped` 可以同时出现：前者是结果状态，后者是粗分类，描述的是同一条记录。具体为什么跳过，还要看错误详情。完整组合在字段参考文档里，此处不用展开全部枚举。

这一步也解释了为什么要保留每轮计划列表：整道题没有产出结果时，单靠已有结果计算的覆盖率可能看不出来。

**这一页让听众记住：成功率回答“做对多少”，覆盖情况决定这个答案能不能信。**

**接到下一步：**“知道有两道做错还不够，我们得打开其中一道，看它为什么错。”

## 第三步：打开一次失败，找第一处错误（3 分钟）

回到修改偏好的任务。仓库本地历史运行 `2026-05-29_044024` 留下过这样的轨迹：

```text
用户要求更新为 light mode
  → Agent 调用 save_memory 保存新偏好
  → 工具返回 saved
  → Agent 告诉用户“已经更新好了”
```

它没有调用 `recall_memory`，只有一次工具调用，低于当时任务要求的两次，因此硬断言失败，Judge 没有继续执行。

可以这样讲：

> 分数告诉我们“没通过”，执行记录告诉我们“它实际做了什么”。现在我们知道它直接保存了新偏好，但还不知道旧偏好是否被替换。下一步应该检查记忆存储和后续召回，才能判断是否真的存在冲突。

这里把执行记录称为 **Trace**。不要把“未先召回”直接讲成“已经证明存储有冲突”；前者是观察，后者仍需证据。

实际演示时，按这条路径打开证据：

1. 在 Dataset 的 Experiment 中选择某个任务的某次尝试，先看 Output 的 `final_response` 和 `tool_calls` 摘要。
2. 打开 `aiden_trace_url`，查看这次任务的 Agent 执行过程。`agent-run` 显示用户目标和最终回复，`agent-response` 显示每次模型调用，工具节点显示参数和实际返回结果。
3. 对照判定依据，找到第一处偏离预期的位置，再检查后续是否恢复。

`sdk-experiment` 中的 `experiment-item-run` 和 `benchmark/<task>#attempt-<n>` 是同一条回放 Trace 的父子节点。实际执行 Trace 在 CI 默认配置的 `benchmark` 环境下。回放的耗时不代表任务执行耗时，Agent 自己的 `success` 也不等于 benchmark 判定通过。

这条链路需要使用包含遥测接入修改的新版本重新运行，旧 Experiment 不会自动补齐。截图默认不上传；链接不可用时，用 `aiden_trace_id` 搜索，并检查 GitHub artifacts 中该尝试的 `history.json`、`episode.json` 和 worker 日志。生成了链接不代表上传已经成功。

也要说明：这是旧版本的真实失败记录，只用于演示排查思路，不能当作当前版本仍然失败的证明。当前实验必须重跑基线。

当我们复核多条失败后，才适合形成“主要失败原因”：例如错误理解页面、选错操作、没有验证完成状态。`failure_class=agent` 本身不会告诉我们这些原因，`first_failure_stage` 的自动覆盖也不完整。

给每条失败记录一个有证据支持的主要原因，找不到就保留未知。如果报告“规划原因占多少”，写清分母是全部有效失败，还是仅已抽查的失败；同一条失败不要重复计入多个主要原因。

**这一页让听众记住：分数发现问题，Trace 支持解释，最终状态验证解释是否成立。**

**接到下一步：**“现在有了证据，我们就可以提出一项具体修改，而不是泛泛地说换个模型试试。”

## 第四步：把发现写成一个优化假设（2 分钟）

先假设当前基线也复现了类似问题，并且存储和召回证据确认旧偏好仍在冲突。

可以把实验写成三行：

```text
观察：修改后仍能召回相互冲突的有效偏好。
假设：更新流程没有正确识别并替换旧偏好。
候选改动：查找相关旧记忆，再按工具支持的语义更新，成功后确认。
```

讲解时强调：

> 我们要改的是产生错误结果的环节。先确认当前工具到底支持什么更新语义，再决定改提示词、工具实现还是记忆检索。一次只测试一项关键变化。

如果当前更新语义本来就会正确替换，或者基线已经通过，就不能根据旧轨迹硬加召回步骤。也不能为了凑够最低工具调用数增加无用操作。应先核查评测要求是否准确，再选择真实存在的问题。

修改前写下验收目标：新偏好持久化正确、新对话选择 light mode、旧值不再作为有效冲突偏好、其他记忆任务没有退化。

**这一页让听众记住：一个优化实验，需要“证据 → 假设 → 改动 → 验收目标”。**

**接到下一步：**“候选版本答对了一次，能说明这项修改有效吗？”

## 第五步：证明它稳定变好，而不是碰巧成功（3 分钟）

只有到这里，才引入重复执行和 k。

> Agent 的结果可能有波动。一次成功能证明它这次做到了，却不能证明它以后也可靠。我们让基线和候选做同一组题，每题重复三次，并查看原来的成功题有没有退化。

以下使用一个独立的两题教学实验，与前面 10 题示例不是同一轮运行。所有尝试都有效：

| 任务 | 基线三次结果 | 候选三次结果 |
| --- | --- | --- |
| 修改偏好 | 失败、成功、失败 | 成功、成功、成功 |
| 召回已保存事实 | 成功、成功、成功 | 成功、成功、成功 |

按人能理解的问题引出指标：

| 先问的问题 | 然后给出的指标名 | 基线 → 候选 |
| --- | --- | --- |
| 第一次就做对了多少题？ | `pass_at_1` | 1/2 → 2/2 |
| 三次中至少做对一次的有多少题？ | `pass_at_k`，这里 k=3 | 2/2 → 2/2 |
| 三次全部做对的有多少题？ | `pass_pow_k`，这里 k=3 | 1/2 → 2/2 |

这样听众就能理解：这份示例里的收益主要是首次表现和稳定性提高，而“至少成功一次”原本就已经达到了。

要让结论成立，两版应使用相同任务、初始状态、Agent 模型、Judge、重复次数和资源条件，只改变要测试的因素。若测试的就是模型，则把模型明确声明为实验变量。保留 Run ID、代码/镜像身份和配置，避免把环境变化误认为优化效果。

三次和两道题仍然只是小规模验证。需要独立复测和未参与调优的变体任务，才能判断结果能否推广。小幅变化、波动较大或证据不完整时，可以得出“证据不足”，不用强行接受或拒绝。

当前定时 runnable 套件的 k 都是 1，不能通过三个 pass 指标区分重复执行的稳定性。即使某题跑了 5 次，suite 中还有题只跑 1 次，suite 的 k 仍为 1。不同日期的运行不会自动合并成 k 次。

**这一页让听众记住：用相同条件对照，看重复结果和新增退化；一次成功不足以完成验收。**

**接到下一步：**“如果它已经做对了，我们还要知道为这次改进付出了多少代价。”

## 第六步：最后看做得够不够快、代价是否合理（2 分钟）

可以这样讲：

> 旧版本可能十秒就回答完成，却留下错误记忆。新版本花十五秒正确更新，这五秒可能值得。接下来我们再找：十五秒里，有没有可以减少的无用等待或重复调用？

此时引入两个耗时指标：**p50 是这批执行的中位数，p90 帮助观察较慢的一批执行。** 不只看一个平均值，也打开最慢的几个任务。

当前 `efficiency.task_wall_ms.p50/p90` 是有效尝试的 Agent 请求耗时，包含失败，且不包含初始化、Judge 等全流程工作。因此直接展示时叫“有效尝试执行耗时”。

若要比较真正的成功完成速度，应另外筛选两版都成功的相同任务/尝试，对比耗时及样本数，同时保留总体成功率、新增成功和新增失败。当前并没有独立导出这份成功样本耗时分布。

发现慢了，再按 Trace 展开：

| 需要回答的问题 | 再查看的诊断信息 |
| --- | --- |
| 是否在绕路或重复操作？ | 工具轨迹、`tool_calls`、`device_actions` |
| 是否在重复推理？ | `llm_calls`、Token、`llm_time_ms` |
| 是否卡在设备动作？ | `device_execution_ms` 和具体工具结果 |
| 是否在反复恢复？ | 错误轨迹、恢复行为；当前 `retry_count` 尚未完整采集 |

Token 是资源用量，不等于美元；当前 runner 没有自动计算 `cost_usd`。Langfuse 默认的 Latency/Cost 列测量上报回放，应使用评测自定义分数。图片相关模型耗时也不能与全部模型耗时重复相加。

这几个边界只在讨论性能时解释，不必放在分享开头。需要精确单位和采集范围时，再查字段参考。

**这一页让听众记住：质量与效率一起验收，减少工作量要以任务仍然正确为前提。**

## 收尾：把这个过程变成下一轮团队工作（1 分钟）

可以这样结束：

> 下一轮我们不需要先优化所有指标。先选一组真实任务，跑出当前结果，找出一类有证据的失败，做一项修改，再用相同条件验证。每次都留下结果和解释，团队就能持续积累哪些改动真正有效。

讲到这里，再展示需求卡片的三个词：

```text
Specify：定义什么叫做对
   ↓
Measure：知道做对多少，打开失败看证据
   ↓
Improve：提出修改，用同条件对照验证效果与代价
```

GitHub Actions 负责重复运行，Langfuse 用来查看和比较记录。它们把证据集中起来，团队仍需要决定任务代表什么、失败证据支持什么假设、怎样才算验收通过。

下一轮的交付物可以先是一张很小的表，不必一开始建设复杂看板：

| 要汇报的内容 | 填什么 |
| --- | --- |
| 我们测了什么？ | 固定任务集、模型/代码版本、k、基线与候选 Run ID |
| 做对了多少？ | 成功数/有效任务数；计划、实际、有效数量；新增失败 |
| 主要哪里错了？ | 一个主要失败模式、代表性 Trace 与最终状态证据 |
| 改了什么？ | 一个假设、一项明确改动 |
| 怎么知道改好了？ | 配对与重复结果、相关任务回归、未参与调优的变体 |
| 代价怎样？ | 可比成功任务的耗时、Token、数值样本数 |
| 下一步是什么？ | 接受/拒绝/证据不足；下一项实验与负责人 |

## 给讲解者的准备清单

分享准备按以下顺序即可：

1. 准备开场的三句对话和第一步的成功条件，让听众先有具体对象。
2. 使用文中的教学表，明确标注“示例”。如已有可比的真实结果，再替换数字并附 Run ID。
3. 准备一条经过核查的失败 Trace。如果展示上述旧记录，说明其版本局限；不要把未知的记忆冲突当作已证实事实。
4. 把每节的“接到下一步”作为讲稿转场，不需要逐字朗读字段和边界说明。
5. 每节只留一个核心画面。完整字段文档与执行命令放在会后资料中。

可以使用的八页标题依次是：**一句“完成了”可信吗 → 什么才算做对 → 做对了多少 → 打开一次失败 → 提出一项修改 → 怎样证明改好了 → 代价是否合理 → 下一轮具体做什么。**

会后需要落地时，再使用[记忆实验步骤与字段参考](./metrics-and-optimization.zh-CN.md)。其中包含 CLI 命令、Langfuse 核对方法、测试入口和详细验收条件。当前 `runner compare` 尚不是自动回归门禁，单元测试通过也不代表产品能力已经提升。
