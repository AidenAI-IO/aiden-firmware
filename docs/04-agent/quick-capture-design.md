# Quick Capture 技术设计：一键记忆屏幕内容

> 状态：设计完成，未实现。
> 开工前需确认一项硬件事实（见「开放问题」）。
> 术语（Screen Memory、Quick Capture、Wakeup 等）定义在 [CONTEXT.md](../../CONTEXT.md)。

## 一句话

用户长按 Aiden 上的按键约 0.8 秒，设备把手机当前屏幕上的内容理解成文字存进长期记忆；之后用户开口问，Aiden 答得出来。

## 用户体验

按住按键，听到一声提示音——表示手势已识别，可以松手。几秒后第二声提示音，表示存好了（失败是另一个音调）。

过后随时可以问：

> "我刚存的那个快递单号是多少"
> "我之前存的那个地址在哪"

Aiden 从记忆里取回并回答。

整个过程不需要说话，也不会打断 Aiden 正在做的任何事——如果它正在执行任务或正在说话，按键照样能存，只是提示音会被跳过。

## 背景

Aiden 已经有语音唤醒和按键唤醒，两者都开启一轮语音对话。用户想记住屏幕上的东西，现有做法是唤醒后说"记住这个屏幕"，然后等 Aiden 截图、理解、保存、回话。

这条路有三个问题。一是慢，要等完整一轮对话。二是有些场合不方便说话。三是它抢占资源——唤醒会打断 Aiden 手头正在做的事。

Quick Capture 把这件事压缩成一个按键动作。

## 范围

**要做的**：按键长按触发；抓取当前屏幕；理解成文本并存入长期记忆；两声提示音反馈；用户开口时能取回。

**不做的**：

- **不做截图归档。** 原图不保留，只留理解出来的文字。
- **不做设备操作经验。** 记的是"屏幕上有什么"，不是"这个 App 怎么操作"——后者是另一套东西（Device Memory）。
- **不做主动提醒。** Aiden 不会主动说"你之前在这里存过东西"，只在用户问的时候答。原因见「已知的局限」。

## 整体流程

```text
用户按住按键
      │
      ▼
┌─────────────────┐
│  手势层         │  按下和松开都记时间，松手时判断：
│                 │  短按 → 走原来的唤醒流程
│                 │  长按 → 走下面的 Quick Capture
└────────┬────────┘
         │ 长按
         ▼
    第一声提示音（可以松手了）
         │
         ▼
┌─────────────────┐
│  抓帧           │  从 frame_service 取一帧当前画面，
│                 │  裁掉黑边只留手机屏幕区域
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  视觉模型       │  一次调用，返回四样东西：
│  （一次调用）   │  一句话摘要 / 关键文本 / 主题词 / 具名事物
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  写入长期记忆   │  作为一条新类型的记忆条目存盘
└────────┬────────┘
         │
         ▼
    第二声提示音（成功 / 失败）
```

任何一步失败就播失败音、什么都不存。

## 三个关键设计决策

这三处都有一个看起来更省事的做法，都被否掉了。每一条都有对应的 ADR 记录原因。

### 一、长按，而不是双击

Quick Capture 需要一个属于自己的触发方式，而设备上的按键已经被唤醒占用了。

双击是第一直觉，但它有个绕不过的代价：判断"这是双击"的唯一办法，是第一次按下之后等 300~400 毫秒看第二次会不会来。等不到才算单击。**于是每一次唤醒都要多等这段时间。** 语音交互是 Aiden 最核心的场景，为一个辅助功能牺牲核心路径的响应速度不划算。

长按不存在这个问题：松手那一刻就知道是短按还是长按，短按立刻走唤醒，零延迟。

代价是长按需要一声提示音告诉用户"到了，可以松手"，否则用户不知道该按多久。这声提示音因此是必需的，不是可选的打磨。

→ [ADR-0001](../adr/0001-quick-capture-uses-long-press.md)

### 二、不走 Agent 的对话流程

看起来最省事的实现是：假装用户说了"记住当前屏幕"，塞给 Agent，让它自己调截图工具和保存工具。零新代码。

但 Agent 每开始一轮任务，第一件事就是中断上一轮，包括停掉正在播放的语音和正在进行的录音。**用户在对话中途按一下按键，这轮对话就没了。**

而且这件事本身没有任何需要 Agent 判断的地方——固定的三步，每步都确定。为它付一轮对话的延迟，还要承担"模型可能忘了调保存工具"的风险，换不到东西。

所以 Quick Capture 是一条独立管线，自己抓帧、自己调模型、自己写盘。

代价是它不出现在对话历史里，也不算一次任务记录。这符合预期：它不是一轮对话。

→ [ADR-0002](../adr/0002-quick-capture-bypasses-the-agent-loop.md)

### 三、不存原图

只存视觉模型理解出来的文字，图本身用完就丢。

原因是存储。长期记忆是受保护数据，设备的自动清理机制永不回收它，而设备在剩余空间低于 5MB 时会进入紧急状态。每张图几百 KB，按几十次就可能把设备卡死，且没有任何自动恢复路径。

代价很实在：**如果视觉模型看漏了或看错了，事后无法补救**，因为原始素材已经没了。这也是为什么失败时选择什么都不存——存个占位条目等以后补全是做不到的，补全需要原图。

→ [ADR-0003](../adr/0003-screen-memory-keeps-no-image.md)

## 触发：两个引脚职责不同

设备上有两个唤醒信号源，接在两个 GPIO 引脚（33 和 32）上：一个是**按键唤醒**，用户手按的实体键；另一个是**语音唤醒**，ASRPro 模块识别到唤醒词后给出的信号。

代码目前对两者一视同仁——同一个回调、同一套去抖。Quick Capture 必须打破这个对称，因为：

**语音唤醒信号是一个脉冲，按不住。** 对它测量"按了多久"没有意义，而且如果脉冲宽度恰好超过阈值，会被误判成 Quick Capture——用户喊一句唤醒词，结果莫名存了一条屏幕记忆。

所以按引脚分职责：

| 引脚     | 职责                   | 处理方式                                |
| -------- | ---------------------- | --------------------------------------- |
| 按键唤醒 | Wakeup + Quick Capture | 监听按下和松开，测量时长，短按/长按分流 |
| 语音唤醒 | 只有 Wakeup            | 保持现状，收到信号就唤醒，不测时长      |

好处是语音唤醒这条路完全不动，它的延迟和误触率零风险。所有改动被限制在按键那一个引脚上。

手势识别做成独立一层（信号 → 手势 → 动作）。这样以后想换成双击，或者给 Quick Capture 单独加一个键，只动这一层，下面的管线不用碰。

### 不需要刷固件

GPIO 通过 sysfs 访问，agent 自己完成引脚的导出和配置，不依赖内核模块或设备树。改动全部落在 agent 二进制内，不涉及内核、DTB 或分区表。

开发期直接替换二进制、重启服务即可验证；正式发布走 OTA 的 `oem` 分区更新，不需要整包烧写。

### 有一处需要在真机上先确认

现有的按键去抖逻辑挂在"按下"这个瞬间，而长按需要"按下 + 松开"这一对信号，两者不兼容，去抖必须重做并挪进手势层。

这是语音交互热路径上的改动，所以：**去抖重做前后的误触率必须在真机上测**，不能只靠单元测试。同理，0.8 秒这个阈值拿在手里合不合适，也要试过才知道。

## 存的是什么

视觉模型一次调用返回四样东西：

| 内容     | 说明                           | 例子                                     |
| -------- | ------------------------------ | ---------------------------------------- |
| 摘要     | 一句话描述这个屏幕             | "微信聊天窗口，对方发来一个顺丰快递单号" |
| 关键文本 | 屏幕上以后可能被问到的具体信息 | 单号 `SF1234567890`                      |
| 主题词   | 用于检索的关键词               | 快递、物流                               |
| 具名事物 | 屏幕上出现的 App、人、服务     | 微信、顺丰                               |

**关键文本这一项不是补充，是这个功能能不能用的前提。**

原因在于检索的工作方式：Aiden 找记忆时，靠主题词和具名事物匹配得分最高，靠正文里的文字匹配得分较低但仍然算。**没有落进文字里的东西，以后就问不出来。** 如果只存一句"对方发来一个快递单号"，用户问"单号是多少"时，Aiden 拿到这条记忆也答不上来——单号本身不在里面。

所以那些具体的串必须原样保留，不能被摘要一句话概括掉。

主题词和具名事物同样是承重的，不是装饰：如果用户的提问和这条记忆在主题词上完全没有交集、正文里也没有出现提问中的字词，这条记忆不是排名靠后，而是**直接被过滤掉**。

## 记忆的生命周期

Screen Memory 作为长期记忆的一个新类别存在。这带来几个必须专门处理的地方——而它们的共同根源是同一件事。

### 主动型记忆 vs 派生型记忆

Aiden 现有的记忆机制是为**派生型记忆**设计的：Agent 干完一件事，从过程里总结出一条经验。这种记忆可能是错的，所以机制里有一整套修正手段——初始可信度不满、根据后续成败升降、被更好的版本取代、发现矛盾时标记冲突。

Screen Memory 是**主动型记忆**：用户看着屏幕，自己按了按钮。它不是推断，是一次观察记录。**它没有对错，只有"当时屏幕上是这样"。**

于是那一整套修正手段施加到它身上，每一条都会产生错误的结果：

**不能被取代。** 现有规则是"同类型 + 主题词重叠 + 具名事物重叠"就认为新的取代旧的，旧的被标记为已替换、从检索中消失。而同一个 App 里存两次，主题词和具名事物几乎必然重叠。**结果是昨天存的被今天存的静默吞掉，用户再也找不到。** 对派生型经验来说"新版本取代旧版本"是对的；对主动型观察来说这是数据丢失——两条记忆不矛盾，它们是两个不同的时刻。

**不能被判为冲突。** 冲突标记是双向的，两条都会被标记，而且这个状态**没有任何恢复路径**。必须保证没有自动机制能把 Screen Memory 推进这个不可逆的状态。

**可信度不该浮动。** 它是用户主动记下的原始观察，恒定为满值。用户问到某个单号、任务顺利完成，不代表这条屏幕记忆"更可信了"——它本来就是确定的。

**过期时间不该被刷新。** 这一条影响最实际。现有机制会在记忆被成功用过之后延长它的过期时间。而过期是 Screen Memory 唯一的自动回收途径（长期记忆不被自动清理），一旦被反复延长，"90 天后过期"就形同虚设——一条经常被问到的记忆会永久占用空间。

### 保留多久

默认 90 天，可以在配置里改，也可以设成永不过期。

选 90 天而不是永久，是因为屏幕内容本身有时效性：验证码、临时地址、某次订单状态，放半年只会污染检索结果。但这是可配的，需要长期保留的用户可以关掉。

### 重复怎么办

同一个屏幕按两次就是两条记忆，这是设计如此，不是待改进项。理由见上面「不能被取代」。

用户想清理，可以直接说"忘掉我存的那个屏幕"——现有的删除能力对它有效。由于没有任何自动合并或取代机制，**手动删除是唯一的用户侧清理手段**，值得专门验证一次。

## Aiden 什么时候会用到它

这一节是整个功能成立的关键。**如果 Aiden 从来不去查这些记忆，那么前面所有的写入逻辑都是死代码。**

### 唯一的入口是 Aiden 自己决定去查

Aiden 曾经在每轮任务开始前做一次自动检索，把相关记忆塞进上下文。那条路已经被移除了（原因是检索结果从未真正进入提示词，只用于遥测统计）。当前的用户画像也不会自动注入。

**所以现在 Aiden 能看到长期记忆的唯一途径，是它自己判断"这个问题需要查记忆"并主动调用检索工具。** 会不会调用，完全取决于提示词里的触发条件和工具自身的说明文字。

这意味着有三处文字必须改。它们不是文案润色，是读取路径的必要条件。

### 三处必须改的说明文字

**一、触发条件里没有"屏幕内容"这一类。** 现在的提示词写的是"当答案依赖已保存的偏好、规则、操作流程或事实时，先调用检索"。用户问"我刚存的那个快递单号"，这既不是偏好也不是规则，按字面读 Aiden 没有理由去查。需要把"用户提到之前看到过、存下过的屏幕内容"明确列进触发条件。

**二、检索工具不知道有这个类别。** 工具的参数说明里逐一解释了现有的几个记忆类别，没有 Screen Memory。Aiden 不知道它存在，就不会去查它。

**三、工具说明里有一句话会主动把这类请求引到错误的地方。** 现在写着"原始的近期对话细节请用另一个工具"。而"我刚才存的那个"听起来正是"近期细节"——Aiden 会去查对话记录，那里面没有 Screen Memory，返回空，于是回答"没找到"。

第三条最隐蔽，因为它不是遗漏，是主动误导。

### 查到之后

Screen Memory 里同时有摘要和关键文本。Aiden 应当直接引用关键文本里的具体信息回答，而不是转述摘要——用户要的是那个单号本身。

这要求关键文本在存储时排版清晰（一行一条，不糊成一段），让模型容易识别。这是内容契约的一部分，不只是格式偏好。

### 已知的局限

召回依赖用户主动问。一键存下来的东西，过一周用户未必记得自己存过——**等于把召回的责任放在了记忆力最差的那一环。**

这是"内容检索"这个目标本身的天花板，不是实现缺陷。要突破就得让 Aiden 主动提及（比如识别到用户回到同一个 App 时提示"你之前在这里存过东西"），那需要把被移除的自动检索以某种形式重新引入，是另一个功能。当前范围内不做，但应当知道上限在哪。

## 反馈

两声提示音，都在设备本地合成，不需要网络也不需要语音合成服务：

| 时刻     | 含义                           |
| -------- | ------------------------------ |
| 按到阈值 | 手势已识别，可以松手了         |
| 流程结束 | 存好了，或者失败了（不同音调） |

**一个已知的取舍**：设备的音频播放是排他的，Aiden 正在说话时提示音会被拒绝。这对"不打扰对话"是正确的，但也意味着恰好在用户最可能处于交互中的时候，反馈消失了。

处理方式是提示音失败绝不影响存储——TTS 期间按键照样存得上，只是没声音。

## 失败处理

任何环节失败——画面取不到、断网、模型额度用完、返回内容无法解析——都是同一个处理：**什么都不存，播失败音，记日志，不重试。**

不重试是有意的：断网时重试几轮，用户要等十几秒才听到失败音，那时人已经走开了。宁可立刻告诉他失败。

这样得到一个干净的保证：**一条 Screen Memory 要么存在且能被查到，要么根本没被写入。** 不会出现"看起来存了、但里面没有任何可查内容"的半成品。

## 配置

新增一节配置项：

```toml
[quick_capture]
enabled = true                 # 关掉就完全恢复现在的行为
long_press_threshold_ms = 800  # 长按阈值
screen_memory_ttl = "90d"      # 保留时长，可设 "forever"
```

`enabled = false` 精确回到当前行为：两个引脚都只做唤醒，不做手势识别。因为改动涉及语音热路径，这个开关是必需的。

## 工作量拆解

按依赖顺序，每一项都可独立验证：

| #   | 内容             | 说明                                                         |
| --- | ---------------- | ------------------------------------------------------------ |
| 1   | 手势层           | 纯时序逻辑，可完全离线用合成信号测试。**先做这个，风险最高** |
| 2   | 引脚职责分离     | 按键引脚接手势层，语音引脚保持原样                           |
| 3   | 抓帧复用         | 把现有截图工具里的取帧和裁边逻辑抽出来共用                   |
| 4   | 视觉调用 + 存储  | 管线主体，含提示词和返回格式约定                             |
| 5   | 记忆生命周期豁免 | 可信度、取代、冲突、过期刷新四处                             |
| 6   | 检索侧文字修改   | 三处说明文字，配套断言测试                                   |
| 7   | 提示音           | 两个新音调                                                   |
| 8   | 配置项           | 含校验                                                       |
| 9   | 真机验证         | 误触率、阈值手感                                             |

第 1 项和第 9 项是风险所在。第 6 项虽然改动量最小，但**漏了它整个功能就是死的**。

## 测试重点

**手势层**最值得测也最容易测——纯时序逻辑，用合成的信号序列覆盖短按、长按、阈值边界、按键抖动、以及按下不松手。

**检索**是最脆弱的地方：能否用只出现在关键文本里的词找到；只按类别查（不带关键词）能否返回；多条之间是否按时间倒序；是否被正确排除在用户画像之外。

**生命周期豁免**必须有回归测试，因为它表现为"到处都是例外"，最容易被后来的人当成遗漏而"修好"。要断言：被成功引用过之后可信度和过期时间都没变；同一屏幕存两次得到两条，且先存的那条仍然能查到——**最后这条是防数据丢失的，最重要。**

**说明文字**要像契约一样断言。没有这几条断言，以后有人整理提示词时会静默切断读取路径，而所有存储层测试依然全绿。

**真机**部分无法替代，是触发部分的准入条件。

## 开放问题

**哪个引脚号对应按键、哪个对应语音？** 已知一个是按键唤醒、一个是语音唤醒，但代码里两者绑同一个回调，看不出对应关系。手势层的设计不受影响，但接线时必须接对——接反了会导致语音唤醒被误判成 Quick Capture，而按键长按没有任何反应。**这是开工前唯一的硬阻塞项。**

**`both` 边沿监听在真机上是否可用。** 属于标准内核能力，极不可能失败，但它是整个方案的地基。真机上一条命令就能确认，建议开工前先跑一次。

几处需要注意的细节：

- 记忆条目的可信度字段**没有默认值兜底**，不显式赋值就是 0，必须显式写满值。
- 可信度恒定还有个必要的副作用：它是检索排序的第三优先级，排在时间倒序之前。只有所有 Screen Memory 的可信度相等，这一级才会平掉、时间倒序才生效。**一旦浮动，被引用过几次的旧记忆会排在刚存的新记忆前面**，直接破坏"我刚存的那个"。
- 时间倒序不需要新增索引字段：记忆 ID 以固定宽度的纳秒时间戳开头，字典序等于时间序。
- 视觉调用走主模型（已具备图像能力），不要用文本模式的那个覆盖配置。
- 管线在 agent 对话循环之外调用模型，现有代码里已有同类先例可参照。
- 存储层不校验记忆类型，新增类型在存储侧零成本；类型枚举只用于向模型说明。
- 保存工具的类型枚举**不要**加入新类型——模型不应该自己手动创建 Screen Memory，只有按键能创建。检索侧要开放，写入侧要关闭。
